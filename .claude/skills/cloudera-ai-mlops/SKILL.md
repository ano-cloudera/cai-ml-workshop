# Cloudera AI (CML) MLOps

Distilled from hands-on work on a real CML credit-risk XGBoost workshop
project — every gotcha below was reproduced and root-caused against a live
CML workspace, not guessed from general docs. Cite the specific mechanism,
not just "it might be a version issue."

## Project structure conventions

A CML project is a git repo mounted into sessions/jobs/deployments. Typical
layout for an ML pipeline project:

```
01_generate_data.py      # numbered scripts = pipeline stage order
02_train_model.py        # each stage is independently runnable AND a CML Job
05_validate_model.py     # KPI gate: exit 0 = pass, exit 1 = fail (CI-compatible)
cml_model.py             # Model Deployment entry point (see below)
cdsw-build.sh            # optional Docker build hook — installs deps + prepares
                          # artifacts baked into the image (runs once at build time,
                          # NOT per-request)
requirements.txt         # pinned deps for the SESSION/JOB/DEPLOYMENT container —
                          # NOT necessarily what a Registry Endpoint serves with
                          # (see AI Registry section)
```

`cdsw-build.sh` runs `set -e` so any step failing aborts the image build —
put data generation + training here only if you want the trained artifacts
baked into the deployment image rather than produced by a separate CML Job.

## The three serving paths — pick the right one

| | Session API | Model Deployment | AI Registry → Model Endpoint |
|---|---|---|---|
| Entry point | Flask/FastAPI route you write | `predict(args)` function, `@cml_model`-decorated | Auto-generated by CML from a registered MLflow artifact |
| Lifecycle | Dies when session closes | Always-on, managed | Always-on, managed |
| Auth | None (session-scoped) | `accessKey` in request body | Session JWT (`/tmp/jwt`) or workspace auth |
| Protocol | Whatever you build | CML's `{accessKey, request}` JSON | KServe V2 / Open Inference tensor protocol |
| Serving container | Your session's container | Built from `requirements.txt` | **Fixed Triton base image**, independent of `requirements.txt` |
| Use for | Interactive dev/demo | Production REST API, custom logic | Standardized model registry + versioning, MLOps governance |

Don't assume these are interchangeable — the request/response contract and
the serving container are genuinely different per path.

## Gotcha 1 — PBJ runtimes need the `@cml_model` decorator, or every request silently fails

CML's PBJ runtimes (`ml-runtime-pbj-*`) do **not** auto-discover the model
function by name. Without `@cml.models_v1.cml_model` on `predict`:
- The deployment **builds and starts fine** — logs show "Model ready", the
  status badge turns green.
- **Every single request then fails** with a bare `400` / `"success": false"`
  and `"failed to execute request"` in the runtime log — no traceback, no
  useful message, because the request never reaches `predict()` at all.

Fix:
```python
try:
    import cml.models_v1 as models
    _cml_model = models.cml_model
except ImportError:                       # local/non-CML execution
    def _cml_model(func=None, **kwargs):
        return func if func else (lambda f: f)

@_cml_model
def predict(args):
    ...
```
The no-op fallback keeps `predict()` callable directly in local tests
(`from cml_model import predict; predict(payload)`) without the CML SDK
installed.

**If you see "Model ready" followed by requests failing with no other
clue, check this first** — it is the single most common root cause of an
unexplained 400 on a CML Model Deployment.

## Gotcha 2 — XGBoost + Gunicorn fork deadlock

Gunicorn forks worker processes *after* the model is loaded in the master.
XGBoost's OpenMP thread pool does not survive a fork safely and can
deadlock on the first `predict()` call in a worker. Fix: force single-
threaded inference before serving —
```python
model.set_params(nthread=1)
os.environ.setdefault("OMP_NUM_THREADS", "1")
```
No real cost for single-row inference. Apply this in both the Session API
(Flask/Gunicorn) and Model Deployment paths.

## Gotcha 3 — `__file__` is undefined inside a CML Model Deployment

CML sends `cml_model.py`'s source to the runtime as a string (like a
Jupyter kernel), not as an imported module — `__file__` raises `NameError`.
Fall back to the environment variable CML always sets:
```python
try:
    _PROJECT_DIR = os.path.dirname(os.path.abspath(__file__))
except NameError:
    _PROJECT_DIR = os.environ.get("CDSW_PROJECT_ROOT", "/home/cdsw")
```

## Gotcha 4 — AI Registry → Endpoint: three compounding bugs

Registering a model via `mlflow.xgboost.log_model()` (or any flavor) for a
**Model Endpoint** (KServe/Triton) hits three separate, easy-to-misdiagnose
failures if done the "obvious" way:

1. **Custom `pyfunc.PythonModel` wrappers silently break.** Triton's
   generated `model.py` calls `self.model.predict(x)` directly. CML's
   conversion produces a `None` model object for a custom `PythonModel`
   class — every inference then fails with `'NoneType' object has no
   attribute 'predict'`, regardless of package versions. **Fix: use the
   native flavor** (`mlflow.xgboost.log_model`, `mlflow.sklearn.log_model`,
   etc.) — Triton has real support for well-known flavors, not arbitrary
   custom classes. Tradeoff: any input preprocessing (e.g. categorical
   encoding) that lived inside the pyfunc wrapper must now happen on the
   caller's side before the request.
2. **`infer_signature()` from a DataFrame produces a ColSpec (named
   columns, no shape) — and CML's converter rejects it for every flavor**
   with `"No shape found in MLflow input"`. Fix: build an explicit
   `TensorSpec` signature by hand:
   ```python
   from mlflow.models.signature import ModelSignature
   from mlflow.types import Schema, TensorSpec
   signature = ModelSignature(
       inputs=Schema([TensorSpec(np.dtype(np.float32), (-1, n_features))]),
       outputs=Schema([TensorSpec(np.dtype(np.float32), (-1,))]),
   )
   ```
3. **dtype must be float32, not float64.** Triton's tensor config for the
   endpoint is fixed at `FP32` (check the endpoint's own `/metadata`
   response) regardless of what the signature says. A float64 signature
   fails at inference time with `"dtype of input float32 does not match
   expected dtype float64"` — mlflow's schema enforcement rejects it before
   `predict()` runs. Declare the signature as float32 to match.

All three must be fixed together — fixing only one still fails.

## Gotcha 5 — the serving container's package versions are NOT your `requirements.txt`

A Model Endpoint created from the AI Registry serves from a **fixed Triton
base image** with its own pinned Python/xgboost/scikit-learn/etc versions —
independent of the project's `requirements.txt` and independent of the
script's `pip_requirements=[...]` argument to `log_model()` (that argument
only *documents* the training environment; it is not installed into the
serving container). Train under the versions the *serving* container
actually ships (check the endpoint's `/metadata` or ask the platform team),
not the versions pinned for your Model Deployment path — those are two
different containers and can legitimately need two different environments
in the same session. If you must alternate, downgrade back to the
project's pinned versions before touching the Model Deployment path again
in the same session; a pickle trained under a much newer `xgboost` major
version may not load correctly in an older serving container (booster
serialization format changes across major versions).

## MLflow / Experiments integration

- `MLFLOW_TRACKING_URI` is auto-set in every CML session — zero config.
- MLflow itself is pre-installed via `mlflow-cml-plugin`. **Do not pin
  `mlflow` in `requirements.txt`** — installing a different version breaks
  the plugin's auth wiring to the workspace tracking server.
- Guard all MLflow usage so scripts still run in environments without it
  (Docker build steps, GitHub Actions):
  ```python
  try:
      import mlflow
      _mlflow_available = True
  except ImportError:
      _mlflow_available = False
  ```
- View results in CML under the **Experiments** tab of the project.

## CML Applications — port binding

CML assigns the listen port via `$CDSW_APP_PORT`, and may have
`$CDSW_READONLY_PORT` already bound to platform infrastructure. Don't
hardcode port 5000 (or any port) — read the env var, and if it's unset or
conflicts, fall back to a small list of candidates:
```python
requested_port = int(os.environ.get("CDSW_APP_PORT", 5000))
readonly_port = int(os.environ.get("CDSW_READONLY_PORT", 0))
if requested_port == readonly_port or not _port_free(requested_port):
    for candidate in (5000, 5001, 9090, 9091):
        if _port_free(candidate):
            requested_port = candidate
            break
```
For Streamlit specifically, CML proxies the Application through a reverse
proxy — disable Streamlit's own CORS/XSRF checks or the UI will silently
fail to load or submit:
```
streamlit run app.py --server.port $CDSW_APP_PORT --server.address 0.0.0.0 \
  --server.enableCORS false --server.enableXsrfProtection false
```

## Security — never hardcode access keys

CML Model Deployment access keys and workspace URLs are secrets/config
that must never be committed. Pattern:
```python
import getpass, os
access_key = os.environ.get("MODEL_ACCESS_KEY") or getpass.getpass("Model access key: ")
```
For workspace URLs (config, not secret, but still environment-specific),
fail loudly with setup instructions rather than embedding one workspace's
URL as a default:
```python
MODEL_URL = os.environ.get("MODEL_URL")
if not MODEL_URL:
    raise SystemExit("ERROR: MODEL_URL not set. Export it from your Model Deployment's own page.")
```

## Debugging checklist — CML Model Deployment returns generic 400s

1. Is `predict` decorated with `@cml.models_v1.cml_model`? (Gotcha 1 — the
   #1 cause.)
2. Does the deployment log say "Model ready" but every request still
   fails? → almost certainly Gotcha 1.
3. Call `predict()` directly in a session first (bypass the HTTP layer
   entirely) to get a real traceback instead of a swallowed 400:
   ```python
   from cml_model import predict
   predict(payload)  # exceptions surface here, not through the deployment wrapper
   ```
4. If deployed via AI Registry/Endpoint instead of `cml_model.py`, check
   the endpoint's `/metadata` for the actual expected tensor name, shape,
   and dtype — don't guess Triton's naming (`INPUT__0`, etc.).
5. Confirm `nthread=1` is set before `predict_proba`/`predict` if the
   model is XGBoost served under Gunicorn (Gotcha 2 deadlocks look like a
   hang or timeout, not a 400 — but worth ruling out first if requests
   never return at all).

## Jobs & scheduling

CML Jobs chain via explicit "Dependency" configuration (Job B runs after
Job A succeeds) or run standalone on a cron-style schedule. Use dependency
chains for a linear pipeline (generate → train → validate) and a
standalone scheduled job for anything that should run independent of
retraining, like periodic data drift monitoring — don't force monitoring
into the training dependency chain just because it's "related."
